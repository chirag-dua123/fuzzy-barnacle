## SAR-Based Flood & Soil Monitoring (Not Optical Satellite)

Most teams will say "we use satellite data" and mean optical imagery (Sentinel-2, Landsat) — which fails exactly when you need it, because monsoon cloud cover blocks optical sensors during the flood event itself. Use **Sentinel-1 SAR (Synthetic Aperture Radar)** instead — it's an active radar sensor that penetrates cloud cover and works day/night.

Technical implementation to cite:

- Pull **Sentinel-1 GRD (Ground Range Detected)** products via the Copernicus Open Access Hub / ESA API
- Use **VV/VH polarization backscatter** — water surfaces produce distinct low-backscatter "dark" signatures compared to vegetation/soil, letting you segment inundation extent directly from radar
- Compute a **change-detection layer**: compare pre-event vs during-event SAR backscatter (simple thresholding or a U-Net segmentation model trained on SAR imagery) to flag newly-flooded pixels in near real time
- Soil moisture proxy: backscatter intensity correlates with surface soil saturation, so this doubles as an input feature for your prediction model, not just a visualization layer

## lead time : **Upstream Watch + Time-to-Reach Prediction**

Instead of a flat "flood risk: high," compute two concrete numbers per village: **distance-to-impact** and **time-to-impact**.

Technical implementation:

- Model the river/drainage network as a **directed graph**, where each node is a monitoring point (upstream gauge, confluence, village) and edges are weighted by river distance and gradient
- Pull upstream discharge/rainfall data from cross-border open sources (Nepal's **DHM — Department of Hydrology and Meteorology**, or similar open hydrology portals) in addition to Indian CWC data
- Estimate flood-wave travel time using a simplified **flood routing model** (e.g. Muskingum-Cunge method, standard in hydrology for propagating a flow hydrograph downstream based on channel geometry and roughness) rather than a naive distance/speed estimate — this is a real, citable hydrological method and will hold up under technical Q&A
- Output per village: *"Flood forming 40km upstream — estimated arrival in 3h 20m,"* updated as new upstream readings come in

## offline siren system : wifi ke thorugh we will send (lora mach )

Telecom towers are typically the first infrastructure to fail in a hilly flood disaster, so the alert must not depend on cellular/internet to reach the last mile.

Technical implementation:

- **LoRa (Long Range radio)** modules at village level form a **mesh network** — each node relays the packet to the next until it reaches all villages downstream, without needing a cell tower or internet backbone
- Alert payload kept minimal (severity code + village ID + time-to-impact, a few bytes) so it transmits fast and reliably over LoRa's low bandwidth
- Each node on receiving the alert can trigger a **local siren via a GPIO relay/microcontroller (ESP32)**automatically, without needing a human in the loop
- Since your team is AI/ML-focused, you can scope this as a **software simulation/protocol design** (model the mesh as a graph, simulate packet propagation and time-to-full-coverage under node failures) rather than a physical build — this still lets you demo "alert reaches 90% of villages even with 60% of cell towers down" convincingly.

## **Auto-generated local-language voice alert**

Many at-risk villagers won't read a dashboard or English SMS, so alerts need to reach them by voice, in their language.

Technical implementation:

- **Text-to-Speech (TTS)** pipeline in regional languages (Assamese, Nepali, Bodo, etc.) — usable open optins include **Coqui TTS**, **Google Cloud TTS**, or India-specific models from **AI4Bharat (Indic TTS)**, which is a natural fit here since it's built specifically for Indian languages
- Alert message auto-templated from your structured alert data (severity + time-to-impact + safe direction), converted to speech, and pushed via IVR call, SMS-to-speech gateway, or the LoRa-siren system's speaker output
- This keeps the whole thing software-generated and dynamic — no team member needs to record anything, it regenerates for any village/language/alert combination on the fly

## **Auto-Generated Evacuation Route with Live Hazard Overlay**

A Google-Maps-style live rerouting system for evacuation, not just a static "evacuate" instruction.

Technical implementation:

- Represent the local road/path network as a **weighted graph**, where edge weights are dynamically updated based on real-time hazard data (a road segment near a rising river or landslide zone gets its weight pushed toward infinity/blocked)
- Run **Dijkstra's or A* shortest-path algorithm** on this graph to compute the safest current route from each village to a designated safe zone/relief camp
- Recompute automatically as new hazard data comes in (e.g. SAR-detected inundation extent or a newly-triggered landslide sensor invalidates a route), pushing an updated route to the same alert channel
- Can be built entirely with open tools — **OSMnx/OpenStreetMap** for the road network graph, overlaid with your live hazard layer

## Kirana Guard: Micro-Relief Warehousing

The last mile is the hardest in disaster relief. Centralized relief camps take days to mobilize, leaving stranded citizens cut off from basic supplies. We transform India's 12 million existing Kirana stores into a resilient, decentralized grid of hyper-local micro-warehouses before disaster even strikes.

Technical implementation:

- **Predictive Stockpiling Pipeline:** Train a **spatiotemporal forecasting model** (e.g., LSTM or XGBoost) combining historical flood data, seasonal forecasts, and local population density to predict optimal emergency kit inventory levels per pincode.
- **Decentralized Node Mapping:** Map registered Kirana stores as distributed nodes in a **graph database** (like Neo4j), tracking the real-time availability and capacity of pre-positioned supplies.
- **Offline-First Distribution Verification:** Implement a low-bandwidth, **QR-based offline authentication system**. Store owners scan a pre-distributed digital token or Aadhaar QR to release supplies, caching the transaction locally via Service Workers until network connectivity is restored.
- **Logistics Impact:** Bypasses completely the traditional 48-hour mobilization delay, achieving zero transportation delays during the most critical window of a disaster.

## ShelterBnB: Community-Led Evacuation Hosting

People routinely refuse to evacuate to government shelters because they cannot bring pets, livestock, or elderly relatives into overcrowded camps. By building a decentralized, community-driven hosting network—an 'Airbnb for emergencies'—we remove these emotional barriers and provide a psychologically safe, dignified temporary home.

Technical implementation:

- **Real-Time Constraint Matching:** Deploy a **bipartite graph matching algorithm** (like Gale-Shapley or a custom weighted allocation) to pair evacuees with hosts based on strict constraints: safe distance, pet/livestock-friendly tags, and elderly accessibility.
- **Host Capacity Management:** Build a lightweight **Progressive Web App (PWA)** and WhatsApp chatbot (via Twilio/Meta API) allowing safe-zone families to pre-register spare rooms or courtyards and toggle availability with a single message.
- **Dynamic Safety Geofencing:** Integrate the host database with the **live hazard overlay (SAR/Flooding)**. If a host's registered location falls into a newly projected risk zone, the system automatically unlists them and re-routes inbound evacuees.
- **Trust & Identity Verification:** Utilize the **Aadhaar/DigiLocker API** for rapid, secure KYC verification of both hosts and evacuees, ensuring absolute safety and accountability within the decentralized network.
